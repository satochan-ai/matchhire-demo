# MatchHire Project Rules

このドキュメントは `match-hire` プロジェクトにおける Antigravity 用プロジェクト固有ルールです。
既存の `AGENTS.md`、`README.md`、`docs/`、および TypeScript 実装コードを根拠として策定されています。

---

## 1. プロジェクトの正式な目的と製品境界

- **目的**: 企業の採用担当者・人事責任者・経営層が、採用ファネル・KPI・ボトルネック・担当者別パフォーマンス・不採用理由等を可視化し、採用プロセスの改善判断を支援する採用支援デモアプリケーションである。
- **主要な管理・分析対象**:
  - `Candidate`（候補者）
  - `Job`（求人）
  - `Application`（応募）
  - `Contact`（スカウト・DM等のアプローチ履歴）
  - `Interview`（面接記録）
  - `Evaluation`（面接評価）
  - `Owner`（採用担当者）
- **境界の明確化**:
  - 本リポジトリは現時点において本番運用向けの認証済み ATS（採用管理システム）そのものではない。
  - 表示画面やドキュメントに記載された将来計画（Supabase移行、LLM活用等）をもって Production ready であるとみなさないこと。

---

## 2. 選考ステータス（CandidateStatus）の厳格な保護 【最重要】

`CandidateStatus` は単なる UI の表示ラベルではなく、採用ファネル、KPI、ボトルネック診断、各種 Analytics 集計に直結する。

### 実在するステータス値
- `応募受付`
- `書類選考`
- `面接`
- `内定`
- `承諾`
- `入社`
- `不採用`
- `辞退`

### 禁止事項
- UI 都合によるステータス名の変更
- ステータスの統合（例: 「不採用」と「辞退」の統合、「内定」と「承諾」の統合）
- ステータスの削除や新規ステータスの無断追加
- 「わかりやすくする」等の理由による意味の改変（例: 「入社」を「内定」と同一視する等）
- ステータス変更は単なる UI 修正ではなく**重大な仕様変更**として扱うこと。

---

## 3. 有効性判定（ValidStatus）の保護

`ValidStatus`（`有効` / `無効` / `未判定`）は、有効応募率や選考通過率などの KPI の分母・分子に直接影響する。

### 禁止事項
- `未判定` を自動的に `無効` として扱うこと
- `未判定` を自動的に `有効` として扱うこと
- UI 表示都合で 3 値を 2 値（有効/無効）に簡略化すること
- 集計都合で `未判定`（unknown）を勝手に排除すること
- **「情報不足（未判定）」と「不適格（無効）」を絶対に混同しないこと。**

---

## 4. アプローチ活動と選考ファネルの完全分離

- **アプローチ活動（母集団形成）**:
  - 対象: `Contact`（スカウト送信、DM送信、開封、返信）
- **選考ファネル（応募後プロセス）**:
  - 対象: `Application`（応募受付、書類選考、面接、内定、承諾、入社、不採用、辞退）

### 運用規律
- スカウト返信率と応募後の書類通過率・面接通過率を同一ファネルとして混在させてはならない。
- KPI の分母・分子を UI 側で独自に統合・変更してはならない。

---

## 5. ルールベース分析と AI 判定境界

現行のインサイトエンジン（`src/lib/insightEngine.ts`）およびボトルネック診断（`src/lib/bottleneck.ts`）は、**TypeScript による決定論的なルールベース処理**である。外部 LLM API（OpenAI / Anthropic / Gemini 等）は使用していない。

### 禁止事項
- 決定論的ルールベースの出力を「AI による合格予測」「採用確率」「AI 合否判定」「LLM 評価」と偽って説明・表記すること。
- 実際には存在しない外部 AI 連携の記述や推測ロジックを追加すること。
- **現行機能は「集計結果から課題・ボトルネック・注意点を提示する補助分析」として扱うこと。**

### 人間による最終判断
- 採用の最終合否判断（pass / reject / offer 等）は**必ず人間が行う**ものとする。
- システム・ルールベースロジックが自動で合否、自動不採用、自動内定、評価確定を行うことはない。

### データ不足の扱い
- 未入力・未判定・情報不足の項目を「不採用」「低評価」「不適格」「NG」と自動解釈してはならない。
- 不足している候補者情報を勝手に推測・補完して評価データを作成してはならない。

---

## 6. 面接評価（Evaluation）の整合性維持

`Evaluation` には `technicalScore`、`communicationScore`、`alignmentScore`、`overallGrade`、`result`、`ngReason`、`concerns`、`comment`、`nextAction` 等が含まれる。

### 禁止事項
- スコア（数値）のみでの自動合否判定
- `null` を 0 点扱いして低評価化すること
- `overallGrade`（評価グレード）と `result`（合否結果）の意味の混同
- UI 都合での不採用理由（`ngReason`）の削除・改変
- 未入力コメントや懸念事項を AI やスクリプトで捏造・補完すること

---

## 7. 候補者個人情報および機密情報の保護

リポジトリ内に存在する候補者データはすべて**ダミーデータ**である。

### 禁止事項
- `src/lib/mockData.ts` や `data/*.csv` 等へ実在の候補者データ（実名、メールアドレス、電話番号、実際の履歴書・職務経歴、年収、面接メモ、評価、不採用理由等）をコピー・コミットすること。
- ドキュメントや README、Git commit message に実候補者情報を記載すること。
- `console.log` 等で Candidate や Evaluation の詳細データをバルク出力すること。
- AI 完了報告やログにセンシティブな個人情報を出力すること。

---

## 8. 書類アップロード機能の誤認防止

- 現状、履歴書・職務経歴書のアップロード、PDF 解析、S3 / クラウドストレージ連携、OCR 機能等は実装されていない。
- 「一般的な ATS だから必要」という理由で勝手にアップロード機能を仮定・追加しないこと。書類アップロードは個人情報保護・ストレージ・認証設計と直結するため、独立した要件定義が必要である。

---

## 9. データソース境界と Repository パターン

データソースは `NEXT_PUBLIC_DATA_SOURCE` 環境変数により以下の 3 モードに分離されている。

1. `mock`: `src/lib/mockData.ts` のインメモリデータ（デフォルト）
2. `csv`: `data/*.csv`（ローカルファイル・API 経由）
3. `sheets`: Google Sheets（GAS 連携・API 経由）

### 運用規律
- データ取得は必ず `src/lib/repositories/` の Repository 層を経由すること。
- UI コンポーネントから直接 CSV や Google Sheets を取得する独自実装を禁止する。
- 3 つのモードを無断で統合したり、mock と本番データを混在させたりしないこと。
- mock データ内のダミー候補者名や求人名を永続的な固定仕様として扱わないこと。

---

## 10. CSV モードの保護

- `data/*.csv` の schema や header を UI 表示都合で安易に変更しないこと。
- CSV schema 変更時は、パーサー、関連 Repository、型定義、ドキュメント（`docs/sheets_schema.md` 等）への影響を必ず確認すること。

---

## 11. Google Sheets / GAS 連携の Secret 保護

- `SHEETS_API_URL` や `SHEETS_API_KEY` はサーバーサイド（Route Handlers）でのみ扱い、クライアントへ露出させないこと。
- 環境変数を `NEXT_PUBLIC_` 化してクライアントコンポーネントへ渡してはならない。
- API キーやエンドポイント実値をコード、ドキュメント、コミットログ、完了報告へハードコードしないこと。

---

## 12. 認証（Auth）および Supabase の未実装境界

- 現在のリポジトリにはログイン、セッション管理、ロール権限（Admin / Recruiter / Interviewer 等）、RLS（行レベルセキュリティ）は実装されていない。
- **現在は本番個人情報を安全に扱える認証済み ATS ではない**ことを前提とすること。
- Supabase 用のディレクトリ枠等が存在していても、現行コードでは未接続・未設定である。
- Supabase が稼働していると誤認してマイグレーションを実行したり、既存の mock/csv/sheets 構成を勝手に Supabase 依存に書き換えてはならない。

---

## 13. 参照中心の現行責務と CRUD / 削除の制限

- 現行実装は一覧、詳細、分析、可視化を中心とした参照系デモアプリである。
- 候補者削除、選考履歴削除、評価削除等の永続削除機能を一般論で安易に追加しないこと（履歴・監査性の保全のため）。

---

## 14. 業務計算ロジックと UI 層の分離

- **ファネル・KPI 計算の正本**: `src/lib/funnel.ts`
- **ボトルネック診断の正本**: `src/lib/bottleneck.ts`
- **インサイト生成の正本**: `src/lib/insightEngine.ts`

### 運用規律
- UI コンポーネント（Recharts、テーブル等）側で独自の再計算を行わないこと。
- チャートデザインや UI レイアウト変更を理由に、業務計算の分母・分子、ゼロ除算処理、閾値判定ロジックを変更してはならない。

---

## 15. 日付処理（Date Format）の保護

- 日付は `YYYY-MM-DD` 形式の ISO 互換文字列として統一されている。
- 期間フィルタや集計（`appliedAt` 基準）が壊れないよう、タイムゾーン変換による意図しない日付ズレや独自フォーマットの導入を避けること。

---

## 16. 求人ステータス（JobStatus）の保護

- 求人ステータス（`募集中` / `停止` / `充足`）は型定義を正本とする。UI バッジの都合等で意味を変更しないこと。

---

## 17. Git の運用安全とコミット履歴の保護

- **作業前確認**: Git操作を行う前に、現在の branch / HEAD / status / ahead・behind を確認すること。現在の ahead・behind 数や一時的な branch 状態を、本ルールファイルへ固定値として記録しないこと。
- **既存作業の保護**: 既存の未push commitや未コミット変更が存在する場合、それをユーザー作業として保護し、無断で書き換え・破棄しないこと。
- **破壊的操作の禁止**: 勝手な `git reset`、`git rebase`、`git commit --amend`、`git stash`、`checkout` 等で既存のコミット履歴や作業を破壊しないこと。
- **`main` ブランチおよび GitHub Pages デプロイの特別扱い**:
  - `main` への push / merge は GitHub Pages の本番公開リリースに直結する。
  - ユーザーからの明示的な指示がない限り、`main` への checkout / merge / push、デプロイワークフロー変更を行わないこと。

---

## 18. 正式な検証コマンド

プロジェクトの `package.json` に実在する検証コマンドを使用すること。

- `npm run dev`: 開発サーバー起動
- `npm run build`: プロダクションビルド検証
- `npm run build:gh`: GitHub Pages 向けビルド検証（`next build --webpack`）
- `npm run lint`: ESLint 静的コード検証（`eslint .`）

*(※ `npm test` や `npm run typecheck` は `package.json` に定義されていないため推測実行しないこと)*

---

## 19. ルール更新の指針（過度に固定しないもの）

以下は実装コード・型定義・設計書を正本とし、本ルールファイルに具体値を固定しすぎないこと。

- 個別のダミー候補者名や求人タイトル
- サンプルデータ件数
- CSS クラス名、カラーコード、個別コンポーネント名
- 全ルート一覧（Next.js App Router の実装を正本とする）

以下のアーキテクチャ・業務モデル変更が発生した場合は、本ルールファイル（`project-rules.md`）の見直しを実施すること。
- `CandidateStatus` / `ValidStatus` の仕様変更
- ファネル集計ロジックの改訂
- データソース方式の変更
- 認証（Auth）や本番 DB（Supabase 等）の導入
- 外部 LLM API の導入
- デプロイ / 公開方式の変更
